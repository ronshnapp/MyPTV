# A worked example for `moving_board_calibration`

Fourteen frames from four synchronized cameras, of a checkerboard held in the
measurement volume and turned about between exposures. Nothing is known about
where the board was in any of them: its pose is recovered from the images
along with the cameras. This is the example for the `moving_board_calibration`
action; the counterpart for `checkerboard_calibration`, where the board sits on
a translation stage, is generated by
`synthetic_data_generation/checkerboard/checkerboard_image_generation.py`.

## Running it

From **inside this folder**, so that the camera files it writes stay here
rather than landing among the ones the main example already has:

```
python ../workflow.py params_file.yml moving_board_calibration
```

It takes a few minutes. It writes a calibration points file and a camera file
for each of the four cameras, so `initial_calibration` is not needed; go on to
`analyze_calibration_error`, or to `final_calibration` to refine further.
`inspect_calibration.ipynb` then looks at the result.

## The data

| | |
|---|---|
| cameras | 4, triggered together, so frame *n* shows one pose of the board seen four ways |
| frames | 14, chosen from a longer sequence to be as unlike one another as possible |
| target | calib.io, 9 x 12 squares, so **8 x 11 internal corners**, 15 mm |
| images | 1800 x 1088, 8 bit greyscale PNG, in `images/<camera>/` |

The images were recorded at half the resolution they are shown here: the
originals are 3600 x 2176 and about 2.5 MB each, which is more than belongs in
a source repository, so they have been averaged down by two. That leaves the
corners roughly 43 px apart, far more than the detector needs, and the example
is still a real one, simply a camera with a smaller sensor.

Note the first frames of the original sequence are dark, the illumination
having not yet settled, and are not included. The detector rejects such frames
of its own accord, but there is no reason to ship them.

## What it should produce

| | |
|---|---|
| boards found | 56 of 56 images |
| reprojection, after the adjustment | about 0.14 px |
| the fitted Tsai model, per camera | 0.09 to 0.23 px |
| rays meeting at the same corner | 0.020 mm |

Two of those deserve a word, because they are the checks that mean something.

**The cameras sit in two pairs**, and the two separations come out at 246.1 mm
and 245.1 mm. Those are recovered independently of one another, and no choice
of lab frame can change them, so their agreeing is a real check on the
geometry rather than a restatement of the fit.

**Triangulating the corners back** through `img_system`, after MyPTV has
fitted its own Tsai model to the calibration points, returns the spacing of
the board as 14.97 mm against its true 15 mm. That is not a free test of the
scale, which is set by declaring the square size; what it tests is everything
downstream of the adjustment.

## About the lab frame

The frame this recovers is anchored on `cam1`, because nothing in images of a
board being turned about says where the origin of the lab frame is or which
way its axes point. The scale is fixed by the size of the squares, so
distances, angles and shapes are right; the origin and the directions of the
axes are a convention. If coordinates have to line up with an apparatus, the
frame has to be related to it afterwards.

## What is here

```
images/cam1 .. cam4/frame01.png .. frame14.png    the images
params_file.yml                                    the settings above
```

Running it adds a `Calibration/` folder with the calibration points, and a
camera file per camera in this folder. Those are deliberately not committed,
being outputs; the point is to produce them.

The image folders are under `images/` rather than here, because the camera
files that the calibration writes are themselves called `cam1` and so on, and
a file cannot be written over a folder of the same name.
